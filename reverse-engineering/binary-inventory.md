# Every byte that differs between the clean executable and gold

> **Documentation standard.** This document follows
> [`../docs/documentation-standard.md`](../docs/documentation-standard.md). Read it before
> editing this file, and check the result still meets it — measured claims only, every site
> tabulated, rejected alternatives and corrections kept visible, and anything untested
> labelled as untested.

**Kind: reference.**

Every other document here is organised by subject: fonts in one, the area map in
another. That answers *"how does fix X work?"* and never answers *"is there
anything in this executable nobody wrote down?"* Those are different questions,
and only the second one catches a stray byte.

This document walks the difference in the other direction. It starts from the
bytes, groups them into runs, and requires a document for every run. It is
generated by [`../tools/build_binary_inventory.py`](../tools/build_binary_inventory.py)
and is meant to be regenerated whenever gold changes.

## 1. The two files

| | |
| --- | --- |
| clean | `build-inputs/swkotornopatch.exe`, 4,042,752 bytes, SHA-256 `761F9466F456A83909036BAEBB5C43167D722387BE66E54617BA20A8C49E9886` |
| gold | `build/kmrp/swkotor_gold_v21_mapnotes.exe`, 4,083,712 bytes, SHA-256 `9ACE45023EAB9063803136E6C312E5E87DD85E07E33CCB5525C04DCA38C478DC` |

**The whole difference, in three numbers:**

| | |
| --- | --- |
| bytes changed inside the original 4,042,752-byte image | **893**, in **77 runs** |
| of those runs, PE header | 13 runs, 296 bytes |
| of those runs, code and data | 64 runs, 597 bytes |
| bytes appended past the end of the original image | **40,960** — ten new 4,096-byte sections |

Runs are formed by merging differing bytes separated by fewer than 8 identical
bytes, so one patch site reads as one row. The threshold is presentation only;
nothing depends on it.

**A calibration for how small 893 bytes is.** It is 0.022% of the image. Every
behavioural change KMRP makes to the executable is either one of these 77 runs or
lives in the appended sections, which no vanilla byte can reach except through
them.

## 2. Reproducing it

```bash
python tools/build_binary_inventory.py \
    build-inputs/swkotornopatch.exe \
    build/kmrp/swkotor_gold_v21_mapnotes.exe
```

It exits 0 only when every code and data run is named by at least one Markdown
document in this repository, and non-zero otherwise, printing the offending
addresses. **That exit code is the point of the tool.** A new patch site with no
write-up fails it.

**What the check does and does not prove.** It proves an address inside the run
— or within 16 bytes before it, so that a document naming an instruction's start
still counts when the difference begins partway through that instruction — is
mentioned in a document. It does **not** prove the document is right, or that it
is the *relevant* document. It catches an undocumented byte; it cannot catch a
byte documented wrongly. Both `VA` and `FILE = VA − 0x400000` forms are searched,
because the reverse-engineering documents use VAs while
[`../docs/universal-resolution-math.md`](../docs/universal-resolution-math.md) and
`src/patcher/KmrpPatcher.cs` use file offsets.

## 3. The PE header, 13 runs

None of these is a patch site. All of them are consequences of appending ten
sections, and a linker would have written the same values.

| VA | FILE | field | clean | gold |
| --- | --- | --- | --- | --- |
| `0x00400916` | `0x000916` | `NumberOfSections` | 4 | 14 |
| `0x0040092C` | `0x00092C` | `SizeOfCode` | `0x33C000` | `0x346000` |
| `0x00400960` | `0x000960` | `SizeOfImage` | `0x46D000` | `0x477000` |
| `0x00400968` | `0x000968` | `CheckSum` | `0x3E73F7` | `0` |
| `0x00400AA8` … `0x00400C37` | `0x000AA8` … `0x000C37` | ten 40-byte section headers | — | see below |

`SizeOfHeaders` stays `0x1000`: the four original section headers end at file
`0x0AA8` and ten more need 400 bytes, which fits inside the existing 4KB of
header without moving anything.

**`CheckSum` is zeroed rather than recomputed.** Windows only enforces the PE
checksum for drivers and for images loaded into a protected process; for an
ordinary user-mode executable, zero means "not present" and the loader does not
care. Recomputing it would be tidier and is not required. Vanilla shipped a
correct one, so this is a small, deliberate loss of tidiness.

**One string is destroyed.** The clean header's padding after the fourth section
header contains the ASCII text `Hellspawn Reborn` at file `0x000AC0`, a leftover
signature from whatever tool last touched the 2003 build. The fifth section
header lands on top of it. It occurs exactly once in the clean image and zero
times in gold; it is inside the header padding, is referenced by nothing, and is
not reachable as data by any code path. Recorded here because "a string
disappeared from the executable" is otherwise an alarming thing to discover.

## 5. Six runs that had no document until this one

The generator's first run reported six code and data runs that no Markdown
document named — every one of them was implemented and explained in a build
script, and none had ever reached a document. That gap is what the tool was
written to find, and this section closes it.

### 5.1 `0x0040B6C7`, `0x0040B6DA`, `0x0040BA6C`, `0x0040BA83` — the baked-in gold resolution

Two shared widget-geometry helpers, vanilla `0x0040B690` and `0x0040BA20`, are
called from essentially every screen that is not the main menu or the HUD. They
recentre a control:

```
newX = originalX − (liveScreenWidth  − DESIGN_WIDTH)  / 2
newY = originalY − (liveScreenHeight − DESIGN_HEIGHT) / 2
```

`DESIGN_WIDTH` and `DESIGN_HEIGHT` reach the code as negated `add eax, imm32`
operands. Gold carries the reference build's own resolution:

| VA | FILE | clean | gold | operand |
| --- | --- | --- | --- | --- |
| `0x0040B6C7` | `0x00B6C7` | `add eax, -640` | `add eax, -3440` | width |
| `0x0040B6DA` | `0x00B6DA` | `add eax, -480` | `add eax, -1440` | height |
| `0x0040BA6C` | `0x00BA6C` | `add eax, -640` | `add eax, -3440` | width |
| `0x0040BA83` | `0x00BA83` | `add eax, -480` | `add eax, -1440` | height |

**This is a bug in gold, not a fix**, and it is the general PC-screen
click-offset bug. Baking 3440x1440 in makes the recentring a no-op at exactly
3440x1440 and wrong everywhere else, drifting in proportion to the distance from
it. `ResolutionPatch` therefore rewrites all four per install
(`NegativeWidthOffsets` / `NegativeHeightOffsets` in `src/patcher/KmrpPatcher.cs`),
so no shipped executable keeps the values gold holds.

They were found by `generate_gold_delta.py` surfacing them as gold-delta chunks
nobody had accounted for, then confirmed by disassembly — the same way this
document's six gaps were found, one layer up. That is the argument for owning a
byte-level inventory rather than trusting per-subject write-ups to be complete.

### 5.2 `0x0045A3B7` and `0x0045A3DC` — two guards that blanked short strings

Both are `jl 0x0045A83C`, six bytes, replaced by six `nop`. `0x0045A83C` zeroes
the entry counts, so `Draw` renders nothing at all.

| VA | condition | vanilla behaviour |
| --- | --- | --- |
| `0x0045A3B7` | `strlen == 1` and `maxWidth < width('o')` | draw nothing |
| `0x0045A3DC` | `strlen <= 2` and `maxWidth < 2 × width('o')` | draw nothing |

Reasonable in vanilla, where they fire only for a hopeless box. The stack-count
label is a fixed 21px while an enlarged font takes `width('o')` to 12px at 1080p
and 16px at 1440p, so **every two-digit stack count silently disappeared**, and
single digits too at 2160p. They run before the wrap loop, which is why patching
the loop alone did not bring the numbers back.

**Removing them is only safe because of the wrap-loop patch** at `0x0045A5E0`. A
box too narrow for one character used to spin forever; with the loop patch it
degrades to one overflowing line instead. The three changes are one set — do not
NOP these guards without it. Full reasoning in
[`../tools/build_wrap_progress_fix.py`](../tools/build_wrap_progress_fix.py);
normal text reaches none of it, since strings of three or more characters skip
both guards.

### 5.3 `0x0062B39B` — the HUD minimap's constructor call, wrapped

```
clean  e8 b0990600    call 0x00694D50     ; CUIMap initialisation
gold   e8 901d2400    call 0x0086D130     ; .kui wrapper
```

Only three bytes of the displacement differ, which is why no document matched
this run: it names neither address, it is a bare relative offset.

The wrapper at `0x0086D130` calls the normal `CUIMap` constructor and then
rewrites **that returned instance and its two child rectangles** back to retail
values. It exists because the area-map work changes the constructor's global
defaults to 1720x720 and 1478x720 — correct for the full map screen, wrong for
the HUD minimap, which is a second consumer of the same constructor. Wrapping
this one call site puts the minimap back without disturbing the full-map
wrappers, which is why the alternative of making the constructor
resolution-aware for everyone was not taken.

`0x00694D50` is identified as map initialisation in
[`map.md`](map.md); the minimap's own geometry is covered in
[`map-scaling.md`](map-scaling.md).

### 5.4 `0x0068C4F4` — two competing width matches in the resource selector

A chain of `cmp eax, imm32` picks a UI resource set by screen width. KMRP
redirects the first comparison to the live width; the later ones would then still
match at 1280 or 1600 and win, so both operands are zeroed to make them
unreachable for any real resolution.

| VA | clean | gold |
| --- | --- | --- |
| `0x0068C4F3` | `cmp eax, 1280` | `cmp eax, 0` |
| `0x0068C4FA` | `cmp eax, 1600` | `cmp eax, 0` |

A screen 0 pixels wide would match, and cannot occur. `0x0068C4E3`, a third width
comparison in the same chain, is **deliberately left alone** — see the comment at
`src/patcher/KmrpPatcher.cs:237`.

## 6. What this document does not establish

* **That each write-up is correct.** §2 states the limit plainly: the check is a
  mention, not a review.
* **That the appended sections are fully documented.** The inventory covers the
  original image. The ten sections' contents are covered by their own subject
  documents, and nothing here re-derives them.
* **That gold is what ships.** It is not. `ResolutionPatch` rewrites the
  constants in §5.1 and elsewhere per install, and the map-note flag in `.kmn` is
  cleared when the user turns the corrections off, so a shipped executable
  differs from gold by design. See
  [`../docs/universal-resolution-math.md`](../docs/universal-resolution-math.md)
  and [`map-markers.md`](map-markers.md) §7.5.
* **That any of it is correct in play.** This is a byte-level audit and makes no
  behavioural claim whatever.
